# Нагрузочный тест: «набег пользователей» на свой сервер

Как со своего компьютера проверить, сколько одновременных людей выдерживает
сервер Shalter, где он начинает тормозить и что ломается первым.

Сценарий — [`scripts/loadtest.k6.js`](scripts/loadtest.k6.js), программа —
[k6](https://k6.io). Уборка после теста —
[`scripts/loadtest-cleanup.js`](scripts/loadtest-cleanup.js).

> Тестируйте только свой сервер. Нагрузка на чужой — это атака, а не тест.

## Что делает тест

Каждый виртуальный пользователь (VU) ведёт себя как живой человек:

1. регистрирует себе аккаунт (email вида `lt_…@loadtest.invalid`);
2. держит WebSocket — как открытая вкладка приложения;
3. по кругу: список чатов → история → «печатает…» → отправка сообщения,
   с паузами 1–6 секунд между действиями;
4. раз за сессию — поиск по переписке (самый тяжёлый из частых запросов).

Сообщения уходят в «Избранное» (чат с самим собой): путь тот же, что у
обычной переписки — шифрование, поисковый указатель, WebSocket, — но
посторонним людям ничего не приходит.

Нагрузка растёт ступенями, чтобы было видно, *при скольких* людях начинает
расти задержка:

| Этап | Длительность | Одновременно |
|---|---|---|
| Разгон | 1 мин | до ¼ от `PEAK` |
| Подъём | 2 мин | до `PEAK` |
| Плато | 3 мин | `PEAK` |
| Спад | 1 мин | до 0 |

## 1. Установить k6 (на своём компьютере)

```bash
sudo snap install k6
```

Или по инструкции для своей системы: https://grafana.com/docs/k6/latest/set-up/install-k6/

## 2. Подготовить сервер

**Резервная копия.** Тест создаёт аккаунты и сообщения в настоящей базе.

```bash
sudo cp -a /путь/к/проекту/data /путь/к/проекту/data.bak
```

Лучше всего — отдельная копия сервера для тестов, чтобы не мешать живым
людям. Если тестируете рабочий — выберите время, когда народу меньше всего.

**Ограничители запросов.** Все VU идут с одного IP — вашего. Без этого шага
тест упрётся в защиту от флуда (ответы `429`), и вы измерите ограничитель,
а не сервер. В `.env` на сервере, на время теста:

```
API_RATE_LIMIT=1000000
AUTH_RATE_LIMIT=100000
```

Если перед приложением стоит nginx с `limit_req` (см.
`deploy/nginx.conf.example`), закомментируйте строку `limit_req zone=general …`
и выполните `sudo nginx -s reload`.

Перезапустите приложение (`pm2 restart shalter` или redeploy в Dokploy).

## 3. Запустить

```bash
k6 run -e BASE=https://ваш-домен -e PEAK=100 scripts/loadtest.k6.js
```

- `BASE` — адрес сервера (без `/` в конце);
- `PEAK` — сколько людей одновременно на пике (по умолчанию 100).

Предел ищется серией прогонов: `PEAK=50`, `100`, `200`, `400`… — пока
задержка не начнёт резко расти или не появятся ошибки.

## 4. Смотреть на сервер во время теста

В отдельном окне, по SSH на сервере:

```bash
htop                 # процессор и память: одно ядро на 100% — это Node
pm2 monit            # или: docker stats — память и CPU самого приложения
df -h                # место на диске
du -sh data/         # рост базы и вложений
```

## 5. Как читать отчёт k6

| Показатель | Что значит | Хорошо, если |
|---|---|---|
| `http_req_duration` p(95) | 95% запросов быстрее этого | < 800 мс |
| `http_req_failed` | доля неудачных запросов | < 1% |
| `shalter_send_message_ms` p(95) | сколько идёт отправка сообщения | < 1000 мс |
| `shalter_failed_steps` | на каком шаге сбои (`step: register / send / ws …`) | 0 |
| `shalter_ws_events` | сколько событий пришло по WebSocket | растёт вместе с отправками |
| `ws_sessions` | сколько WebSocket-соединений открылось | ≈ число VU |

Пороги из таблицы прописаны в самом сценарии: если какой-то не выдержан,
k6 напишет это в конце и завершится с ошибкой.

**Где искать причину:**

- растёт `http_req_duration`, а процессор на сервере на 100% — упёрлись в
  одно ядро: Node и SQLite работают в одном процессе (см. AGENTS.md и
  DEPLOY.md — «run exactly one instance»). Помогает более быстрый процессор,
  а не второй экземпляр;
- много `429` — не подняты ограничители из шага 2;
- ошибки на `register` — чаще всего совпадение телефона/юзернейма у двух VU
  (случайные, но не уникальные) — на нескольких штуках это нормально;
- ошибки `500` на `send` при большой нагрузке — см. «Известные слабые места»;
- `ws-connect` падает — проверьте, что nginx пропускает `Upgrade` для `/ws`.

## 6. Ограничения теста с одного компьютера

Домашний компьютер и домашний интернет вытянут примерно от нескольких сотен
до пары тысяч таких пользователей — дальше упрётся уже ваш канал и
процессор, а не сервер. Признак: на сервере CPU далеко не на пределе, а
задержки растут. Для большей нагрузки k6 запускают с нескольких машин
одновременно или из облака (Grafana Cloud k6).

## 7. После теста

**Удалить тестовые аккаунты** — на сервере, из папки проекта:

```bash
npm run loadtest:cleanup -- --dry-run   # сколько их
npm run loadtest:cleanup                # удалить
```

Удаляются только аккаунты с email на `@loadtest.invalid` — тем же путём,
что «Удалить аккаунт» в настройках: вместе с их чатами, сообщениями и
сессиями.

**Вернуть ограничители:** уберите `API_RATE_LIMIT` / `AUTH_RATE_LIMIT` из
`.env`, раскомментируйте `limit_req` в nginx, перезапустите приложение и
`sudo nginx -s reload`.

## Известные слабые места

Найдены при подготовке теста; нагрузка их, скорее всего, покажет.

- **Идентификаторы из времени.** Сообщения, чаты и аккаунты получают id вида
  `m_${Date.now()}`. Два сообщения в одну миллисекунду — второе падает с
  `500` (повтор первичного ключа). При одном человеке не видно, под
  нагрузкой — первые ошибки в отчёте. Лечится случайным хвостом к id.
- **Вход по неподписанной cookie.** `session_uids` — просто список id
  пользователей без подписи (server/middleware/auth.js). Это не про
  нагрузку, а про безопасность: подменив cookie, можно войти в чужой
  аккаунт. Исправлять до любого публичного запуска.
