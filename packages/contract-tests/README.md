# Тесты Shalter

Набор фиксирует **внешнее поведение** приложения перед миграцией на NestJS + React.
Те же тесты потом проверяют новый код: модуль считается перенесённым, когда его
тесты зелёные на новой реализации.

```
npm run test:contract     # контрактные API/WS + совместимость данных + unit (Vitest)
npm run test:unit         # только unit (packages/contract-tests/unit, бывший test/ на node:test)
npm run test:e2e          # сценарии в браузере (Playwright)
npm run test:types        # проверка типов TypeScript в packages/contract-tests/
```

- `contract/` — чёрный ящик по HTTP/WS, папка на модуль.
- `compat/` — фикстура `data/` (база + зашифрованные файлы с ротацией ключей),
  созданная текущим сервером; новая реализация обязана читать её байт в байт.
  Пересборка — только на текущем legacy-сервере, см. `compat/README.md`.
- `unit/` — unit-тесты чистой логики; им, в отличие от контрактных, можно
  импортировать `server/`.
- `e2e/` — Playwright.

Отдельный файл или папка: `npx vitest run --config packages/contract-tests/vitest.config.ts contract/auth`.

## Как устроено

- `support/server.ts` поднимает сервер **отдельным процессом** на свободном порту
  с cwd во временной папке. Все модули сервера берут данные из `process.cwd()/data`,
  поэтому у каждого файла тестов своя чистая база, uploads и outbox.
  Окружение собирается с нуля: SMTP, S3, ключи AI и платёжек разработчика в тесты
  не попадают. `SHALTER_TEST_MODE=1` выключает фоновые обходы и RTMP.
  Обход по таймеру тест прогоняет сам: `POST /api/test/sweeps/:name` (есть только в
  этом режиме) выполняет один проход в фоновом процессе, `now` в теле переводит часы
  обхода (`contract/sweeps`).
- `TARGET=legacy` (по умолчанию) — `server/index.js`; `TARGET=nest` — каркас NestJS `apps/api` (сначала `npm run build:api`); ещё не перенесённое он отдаёт старому приложению.
  `TEST_BASE_URL=http://…` — гнать тесты против уже запущенного сервера
  (тесты, которым нужен каталог данных, тогда пропускаются).
- `KEEP_TEST_DATA=1` — не удалять временные папки (там же `server.log`).
- **Без сети.** Сервер запускается со сторожем `support/net-guard.cjs`: соединения и
  DNS-запросы не на localhost отклоняются, как будто сети нет, и `stop()` роняет файл
  со списком адресов. Если модуль сам ходит наружу (превью ссылок, перевод, push),
  его трафик заворачивают в локальную заглушку: `contract/integrations/stubs.ts`
  (`useEgressProxy`), а в e2e это фикстура `egress` (`e2e/support/egress.ts`).
  Адреса внешних «сайтов» берутся из TEST-NET (203.0.113.x), без DNS. Браузер в e2e
  обрывает все запросы не на localhost, неожиданный внешний адрес роняет тест
  (`blockInternet` в `e2e/support/fixtures.ts`).

## Правила для контрактных тестов

1. **Чёрный ящик.** Тесты не импортируют ничего из `server/` и не читают базу.
   Данные создаются и проверяются только через HTTP и WebSocket (`support/seed.ts`).
   Исключение — то, что сервер сам кладёт на диск как внешний артефакт
   (письма в `data/outbox` вместо SMTP).
2. **Форма — строгими схемами.** `schemas/*.ts` — `z.strictObject`: лишнее поле
   такая же ошибка, как пропавшее. Условные поля (`undefined` → ключа нет в JSON)
   помечены `.optional()`, и список взят из исходников (`rowTo*`), а не угадан.
   Сами схемы лежат в `packages/shared/src/schemas` (их же берёт новый клиент
   `apps/web`), а `schemas/*.ts` здесь только реэкспортируют их.
3. **Значения — точечно.** `toMatchObject` для значимых полей; тексты ошибок
   сверяются точно — их видит пользователь.
4. **Побочные эффекты обязательны.** Действие → WS-событие нужным людям (и *не*
   пришло посторонним) → изменилось состояние, видимое через API.
5. **Фиксируем текущее поведение.** Тесты должны проходить на текущем коде. Если
   поведение выглядит ошибкой, тест всё равно фиксирует его как есть, с комментарием
   `// ПОВЕДЕНИЕ-ВОПРОС: …`; такие места решаются отдельно — чинятся до переноса или
   переносятся как есть.
6. Один `useServer()` на файл; тесты внутри файла идут по порядку, файлы — параллельно
   и в любом порядке (проверка: `--sequence.shuffle.files`).
