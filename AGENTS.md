# Migration in progress: Express + vanilla JS → NestJS + React

The project is moving module by module from plain Express (`server/`) and framework-free JS (`public/`) to a NestJS backend (`apps/api`) and, later, a React frontend (`apps/web`). The plan and its progress live in the migration plan doc; check it before starting a migration step. Until a part is migrated, the old code is the production code. Keep it working, and don't port it ahead of the plan.

## Layout (npm workspaces, not pnpm)

- `server/` is the legacy Express backend (CommonJS) and still serves everything that hasn't moved. `server/app.js` builds the Express app. `server/runtime.js` runs what lives next to the HTTP server: WS, the background worker, RTMP, push, and shutdown. Under `apps/api` the WS gateway is Nest's (`modules/realtime`): `startRuntime` gets it as `opts.realtime`, skips `attachWebSocketServer`, and `server/ws.js` forwards every `broadcastToUsers` and worker-relayed event to it. `server/index.js` is the standalone entry point, and production still runs it.
- `apps/api` is NestJS 12 on the Express adapter (TypeScript, ESM, `npm run build:api` → `apps/api/dist/main.js`). It mounts the whole legacy app as a fallback: Nest routes run first, and any path Nest has no route for goes to `server/app.js` (`src/legacy/legacy-fallback.adapter.ts`). The per-request pipeline (security headers, compression, cookies, JSON body, rate limits, `Cache-Control`, errors from those steps) is `server/front.js`, shared by both backends and run exactly once per request (`src/legacy/front.middleware.ts`). Migrating a module means adding its Nest module; Nest's route shadows the legacy one. The legacy router stays mounted in `server/app.js` until production runs `apps/api` (the fallback and rollback path), then migrated routers are deleted.
- `packages/contract-tests` holds the test suite (Vitest + Playwright). It pins behaviour, and both targets must pass: `TARGET=legacy` (default) and `TARGET=nest` (build `apps/api` first). See its README.
- `public/` stays framework-free native ES modules until stage 4 (React + Vite in `apps/web`). No JSX, TS, or bundler-only syntax there. `npm run build` (esbuild) is only packaging, and `npm run dev` serves the raw source.

## Backend architecture (`apps/api`): classic NestJS MVC

Same layout as alex-dispatch-backend.

```
src/
  main.ts  app.module.ts
  common/   cross-module: errors/ (ApiError), filters/, interceptors/, pipes/, lib/, types/
  legacy/   the bridge to server/: fallback adapter, shared front pipeline, typed requires of legacy modules
  modules/<name>/
    <name>.module.ts  <name>.controller.ts  <name>.service.ts  <name>.repository.ts
    guards/  pipes/  decorators/  stores/ (in-memory state)  lib/  (only what the module needs)
    model/domain.ts            types: row types (`$inferSelect`) and API entities
    model/schemas/*.schema.ts  Zod request schemas + `z.infer` DTO types
```

- **Controller** = HTTP only: route, guards, params, `@Body(new ZodValidationPipe(schema)) dto` (bind the pipe on the parameter, never method-level `@UsePipes`), cookies. It calls the service and returns its result. `@HttpCode(200)` on POST (Nest defaults to 201, the API answers 200).
- **Service** = business logic. It throws `ApiError(status, text)` for API errors, so the body stays `{ error: "…" }` as in `server/`.
- **Repository** = Drizzle queries only, no logic. Only repositories touch `Db`.
- **Bridge to `server/`.** Whatever Nest still needs from unmigrated parts (bots and AI responders, Hugo and Shalter AI accounts and quotas, uploads access, file storage, live streams, TURN credentials, join approval, system chat, mail, push, account deletion, WebAuthn, link previews and instant view, LanguageTool, data export, pricing, donation orders and the DonationAlerts connection) goes through typed wrappers in `src/legacy/legacy.ts`, required lazily on first call (those modules open the DB when loaded). Pure logic and in-memory state that only migrated routes use are ported to TS instead (`common/lib/`, `modules/*/stores/`). The legacy copy stays until `server/` is gone. A bug fix there goes into both.
- **Users, chats, messages, topics.** `modules/users/lib/user.mapper.ts` and `user.presenter.ts` mirror `rowToUser` (`server/data/users.js`) and `publicUser`/`selfUser` (`server/data/sanitize.js`); `modules/chats/lib/chat.mapper.ts` and `ChatsRepository` mirror `rowToChat`, `createChat` and `updateChat` (`server/data/chats.js`); `modules/messages/lib/message.mapper.ts`, `message-edits.ts` and `MessagesRepository` mirror `rowToMessage`, `addMessage` and the `mutate`-based edits (`server/data/messages.js`); `TopicsRepository` mirrors `server/data/topics.js`; `PaidMediaRepository` mirrors `server/data/paidMedia.js`; `ScheduledMessagesRepository` and `lib/scheduled-repeat.ts` mirror `server/data/scheduledMessages.js` (`scheduled-repeat.spec.ts` fails if repeats drift), and `ScheduledDeliveryService` is `server/lib/scheduledMessagesSweep.js`: under `apps/api` it sends scheduled messages (bot API ones included) and `startRuntime` gets `opts.ownScheduledSweep` and doesn't start the legacy sweep. `modules/users` is only the data layer (chats and messages import it), contacts, privacy, stars (`StarsRepository`, `server/data/stars.js`) and user settings included: `ContactsRepository` and `lib/contact-note.ts` mirror `server/data/contacts.js` (notes are sealed by `textCrypto()`, same AAD); `UserSettingsService` and `lib/settings.defaults.ts` mirror `server/data/settings.js` (`settings.defaults.spec.ts` fails if `DEFAULT_SETTINGS` drifts). `UserPrivacyService` and `lib/privacy-rules.ts` mirror `server/lib/privacyRules.js` (`privacy-rules.spec.ts` fails if the rules drift). The `/api/users` routes live in `modules/profiles` (with `/api/avatars`, `/api/status` and `/api/profile-track`: `lib/avatars.ts` and `lib/profile-status.ts` mirror `server/lib/avatars.js` and `profileStatus.js`, `avatars.spec.ts` fails on drift; the status catalog is only read there, the admin panel in `server/` edits it), `/api/settings` in `modules/settings` (both import chats and messages) `/api/contacts` in `modules/contacts`, `/api/stars` in `modules/stars`, `/api/bootstrap` in `modules/bootstrap`, `/api/search` in `modules/search`, `/api/push` in `modules/push` (subscriptions only; sending stays in `server/push.js`), `/api/stickers` and `/api/custom-emoji` in `modules/stickers` (stickers and emoji scenes are still cleaned by `server/lib/sanitizeSticker.js`/`sanitizeScene.js` through the bridge), `/api/usernames` in `modules/usernames` (auctions and the username market; `checkUsername` stays in `server/lib/username.js`), `/api/channels` in `modules/channels` (catalog, similar channels, subscribe, stats; `ChatsRepository.similarChannels` mirrors `similarChannels` in `server/data/chats.js`), `/api/posts` in `modules/posts` (channel posts, views and comments; comments go through `MessageSendService` like any message), `/api/stories` in `modules/stories` (`StoriesRepository` and `lib/story.mapper.ts` mirror `server/data/stories.js`, `StoryAudienceService` mirrors `server/lib/storyAudience.js` and `visibleAuthorIds`; story videos are still processed by the worker in `server/`), `/api/nearby` and `/api/geo` in `modules/nearby` (`lib/nearby-distance.ts` mirrors `server/data/nearby.js`), `/api/hugo`, `/api/link-check`, `/api/export` and `/s/:code` with `/api/short-links` in `modules/hugo`, `link-check`, `export` and `short-links`, `/api/support`, `/api/partners` and `/api/ai` in `modules/support`, `partners` and `shalter-ai`, `/api/premium` and `/api/business` in `modules/premium` (prices and plans stay in `server/data/pricing.js`), `/api/translate` in `modules/translate`, `/api/donation-alerts` in `modules/donation-alerts` (OAuth and polling stay in `server/lib/donationAlerts.js`), `/app/:username` (bot mini-app pages) in `modules/mini-apps`, `/api/reports` in `modules/reports` (filing a report and resolving it from the moderator's report message; the admin panel's report lists stay in `server/`), `/share-target` with `/api/share/:token` in `modules/share-target` (the Web Share Target box is in-memory, so both moved together), `/api/downloads` in `modules/downloads` (app builds from `public/downloads` and the latest GitHub release), `/api/oauth` in `modules/oauth` (Sign in with Shalter: apps, codes and tokens, `OAuthRepository` mirrors `server/data/oauthApps.js`); and `ProfileNotifyService` mirrors `server/lib/notifyProfileChanged.js`. `user.mapper.spec.ts`, `chat.mapper.spec.ts` and `message.mapper.spec.ts` fail if they drift. A change to either side goes into both.
- **Encryption stays in `server/`.** Message text and voice transcripts are sealed and opened by `server/lib/textCrypto.js` (keys, `crypto_keys` rotation, secret-chat keys) through the bridge (`textCrypto()`), so both backends write the same ciphertext format. Files are the same: storage (disk/S3), file encryption, compression and serving (`server/lib/storage.js`, `fileCrypto.js`, `fileCompression.js`, `serveUpload.js`) are reached through the bridge, and `modules/uploads` only checks access and streams the request into them. Don't port any of it to TS until `server/` is gone.
- **Route order.** Nest registers routes in controller order (`controllers: [...]` in the module), then method order. A static path (`by-username/:username`, `invite/:code`) must come before a `:id/...` path it could match.
- Explicit `public` on methods, `private readonly` constructor injection. A module exports only what other modules need. Cross-cutting guards live in the owning module (`modules/auth/guards/auth.guard.ts`) and that module is `@Global()`.
- Unit tests are `*.spec.ts` next to the source (`npm run test:api`). Behaviour is pinned by `packages/contract-tests`.

## Frontend architecture (`apps/web`, stage 4): FSD 2.0

Same as alex-dispatch carrier-crm and et-app guide-app: layers `app → views → widgets → features → entities → shared` (`views` instead of `pages`). A slice imports only lower layers, other slices only through their public `index.ts`, and inside a slice only relative imports. This is enforced with `no-restricted-imports` per layer, as in carrier-crm's `eslint.config.js`. Segments: `api/` (transport + TanStack Query `queryOptions`, owns `baseKey`), `model/` (types, hooks, state), `ui/`, `lib/`, `config/`. Server state lives in TanStack Query, and API/WS types come from `packages/shared`.

## Rules that hold across the migration

- **Feature freeze until the core (auth, chats, messages, uploads, WS, calls) is migrated** (decided 2026-10-21): no new features in either backend, only bug fixes.
- **New backend code is TypeScript in `apps/api`.** Don't add new modules to `server/`. Fix bugs where the code currently lives.
- **Never mount the legacy app as an Express sub-app inside Nest.** Express 5 (Nest) would swap its req/res prototypes. Keep the wrappers in `src/legacy/`.
- **Behaviour doesn't change during a move.** A migrated module is done when its contract tests are green on `TARGET=nest` without edits to the tests. Any intentional behaviour change in either backend must keep `npm run test:contract` green on both targets.
- **Contract tests are black-box** (HTTP/WS only, never import `server/` or `apps/`). Write tests for a module before migrating it if it has none.
- **Data:** SQLite at `data/app.db` (`better-sqlite3`, schema in `server/db.js`), accessed only through the `server/data/*.js` modules or, in `apps/api`, through repositories built on Drizzle (`apps/api/src/modules/db`: `DbModule` wraps the very connection `server/db.js` opens, and queries stay synchronous). `server/db.js` owns the schema: `apps/api/src/modules/db/schema.ts` only describes it (columns and primary keys), `schema.spec.ts` (`npm run test:api`) fails on drift, and drizzle-kit `generate`/`migrate`/`push` are not used until `server/` is gone. A schema change goes into `server/db.js` first, then re-run `npx drizzle-kit pull` in `apps/api` (or edit `schema.ts` by hand). Never query the connection from a route handler, controller or service. Relational data (chat membership, call participants) lives in join tables. Nested, never cross-queried fields stay as JSON TEXT columns on the parent row. Encrypted data (messages, files, key rotation) must stay byte-compatible: `packages/contract-tests/compat` is the fixture that proves it.
- **One API process per `data/` directory.** Typing presence and WS connections are in-memory. The background worker `server/worker.js` is forked by the runtime itself for timer sweeps and the `background_jobs` queue, and reaches clients only by relaying WS events (`server/lib/workerBridge.js`). Never start it separately.
- Call signaling is WebSocket-first (`server/ws.js`, in Nest `modules/realtime/ws.gateway.ts`, which hands `call:signal:send` to `CallSignalsService` in `modules/calls`; client `public/js/lib/wsClient.js`). HTTP polling is only a reconnect fallback, and both paths store the signal the same way.
- **WS events in Nest go through `RealtimeService`** (injected, `RealtimeModule` is global), never through `server/ws.js`. The WS protocol (`{ type, … }` both ways, cookie auth on upgrade, close code 4001) is why the gateway is a plain provider on Nest's HTTP server and not a `@nestjs/websockets` gateway.
- The client-side router (`public/js/router.js`) keeps the shell (nav rail, chat list, an in-progress call's PiP bubble) mounted across navigation. Route views live in `public/js/views/`.
- Deploys are done by someone else: any server-side step goes into DEPLOY.md as runnable commands.
