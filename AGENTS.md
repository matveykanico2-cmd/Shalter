# Migration in progress: Express + vanilla JS → NestJS + React

The project is moving module by module from plain Express (`server/`) and framework-free JS to a NestJS backend (`apps/api`) and a React frontend (`apps/web`). The client has been switched over (stage 4 done): `apps/web` is the only client, the old one (`public/js`) is gone. The plan and its progress live in the migration plan doc; check it before starting a migration step. Until a backend part is migrated, the old code is the production code. Keep it working, and don't port it ahead of the plan.

## Layout (npm workspaces, not pnpm)

- `server/` is the legacy Express backend (CommonJS) and still serves everything that hasn't moved. `server/app.js` builds the Express app. `server/runtime.js` runs what lives next to the HTTP server: WS, the background worker, RTMP, push, and shutdown. Under `apps/api` the WS gateway is Nest's (`modules/realtime`): `startRuntime` gets it as `opts.realtime`, skips `attachWebSocketServer`, and `server/ws.js` forwards every `broadcastToUsers` and worker-relayed event to it. The background worker is Nest's too: `startRuntime` forks `opts.workerEntry` (`apps/api/dist/worker.js`, built from `src/worker.ts`) instead of `server/worker.js`, over the same IPC protocol (`server/lib/workerBridge.js`), and with `BACKGROUND_WORKER=0` `main.ts` runs the queue and sweeps itself (`opts.ownBackground`). `server/index.js` is the standalone entry point, and production still runs it.
- `apps/api` is NestJS 12 on the Express adapter (TypeScript, ESM, `npm run build:api` → `apps/api/dist/main.js`). Nest routes run first. Any path Nest has no route for goes to the client files (`src/static`: the client build in `/assets` from `apps/web/dist`, `/.well-known`, the doc and promo pages, the asset packs, `public/` and the client's `index.html` for every app path, in `server/app.js` order and with the same `serve-static`/`send`/`express-static-gzip` so headers match), then to the whole legacy app (`server/app.js`) as a last resort (`src/legacy/legacy-fallback.adapter.ts`). The per-request pipeline (security headers, compression, cookies, JSON body, rate limits, `Cache-Control`, errors from those steps) is `server/front.js`, shared by both backends and run exactly once per request (`src/legacy/front.middleware.ts`). Migrating a module means adding its Nest module; Nest's route shadows the legacy one. The legacy router stays mounted in `server/app.js` until production runs `apps/api` (the fallback and rollback path), then migrated routers are deleted.
- `packages/contract-tests` holds the test suite (Vitest + Playwright). It pins behaviour, and both targets must pass: `TARGET=legacy` (default) and `TARGET=nest` (build `apps/api` first). Contract tests serve a stub client build (`fixtures/web-dist`); the Playwright scenarios run on the real one (`npm run build:web` first, or `WEB_DIST=<folder>`). See its README.
- `packages/shared` holds the API response schemas (Zod, `src/schemas/*.ts`, imported as `@shalter/shared/schemas/<name>`). The contract tests pin responses with them (`packages/contract-tests/schemas/*.ts` only re-export), and `apps/web` takes its API types from them (`import type`, so Zod isn't bundled). A response change goes into the schema here.
- `public/` holds static files only: the doc, promo and download pages with their styles (`public/styles`), icons, images, the PWA manifest and `sw.js`, gift scenes, app builds (`public/downloads`), the bot mini-app SDK at the public URL `/js/shalter-web-app.js` and third-party players in `public/js/vendor`. No client code lives there any more.
- `apps/web` is the client (Vite + React 19 + react-router 8, SPA). Both backends serve its build `apps/web/dist` (`SHALTER_WEB_DIST` overrides the folder); without a build the app's pages answer 503. `npm run build` = Vite build + `scripts/build.js` (precompressed `.br`/`.gz`, `build.json` with the version for `/api/version`, unpacked image packs for nginx). In development `npm run dev:web` starts Vite on :5173 and proxies `/api`, `/ws`, `/uploads` and the static paths to the backend (`SHALTER_API_URL`, default `http://localhost:3000`). `npm run test:web` = ESLint (layer boundaries) + Vitest (jsdom), `npm run build:web` = typecheck + build. The native shells (Capacitor `capacitor.config.json`, Tauri `src-tauri`) open the live site, so they get the client from the server; the page keeps the bridges they call (`window.__shalterOpen`, `window.shalterDesktop`).
- TypeScript: the root has TS 6 (`apps/web` and its ESLint: typescript-eslint doesn't support TS 7 yet), `apps/api`, `packages/contract-tests` and `packages/shared` have their own TS 7. Run `tsc` from the package (`npx tsc` there or its npm script), not from the root.

## Backend architecture (`apps/api`): classic NestJS MVC

Same layout as alex-dispatch-backend.

```
src/
  main.ts  app.module.ts
  common/   cross-module: errors/ (ApiError), filters/, interceptors/, pipes/, lib/, types/
  legacy/   the bridge to server/: fallback adapter, shared front pipeline, typed requires of legacy modules
  static/   client files and the SPA fallback (what server/app.js serves after its routes)
  modules/<name>/
    <name>.module.ts  <name>.controller.ts  <name>.service.ts  <name>.repository.ts
    guards/  pipes/  decorators/  stores/ (in-memory state)  lib/  (only what the module needs)
    model/domain.ts            types: row types (`$inferSelect`) and API entities
    model/schemas/*.schema.ts  Zod request schemas + `z.infer` DTO types
```

- **Controller** = HTTP only: route, guards, params, `@Body(new ZodValidationPipe(schema)) dto` (bind the pipe on the parameter, never method-level `@UsePipes`), cookies. It calls the service and returns its result. `@HttpCode(200)` on POST (Nest defaults to 201, the API answers 200).
- **Service** = business logic. It throws `ApiError(status, text)` for API errors, so the body stays `{ error: "…" }` as in `server/`.
- **Repository** = Drizzle queries only, no logic. Only repositories touch `Db`.
- **Bridge to `server/`.** Whatever Nest still needs from unmigrated parts (bots and AI responders, Hugo and Shalter AI accounts and quotas, uploads access, file storage, the RTMP ingest for live streams, media previews and duration probes (sharp, ffmpeg) with fetching an upload to a temp file and storing the result, the donation polls (DonationAlerts, DonatePay) and moving uploads to S3 (started by `startLegacySweeps`), TURN credentials, join approval, system chat, mail, push, account deletion, WebAuthn, link previews and instant view, LanguageTool, data export, pricing, donation orders and the DonationAlerts connection, gift GIF processing) goes through typed wrappers in `src/legacy/legacy.ts`, required lazily on first call (those modules open the DB when loaded). Pure logic and in-memory state that only migrated routes use are ported to TS instead (`common/lib/`, `modules/*/stores/`). The legacy copy stays until `server/` is gone. ## Frontend architecture (`apps/web`): FSD 2.0

Same as alex-dispatch carrier-crm and et-app guide-app: layers `app → views → widgets → features → entities → shared` (`views` instead of `pages`). A slice imports only lower layers, other slices only through their public `index.ts`, and inside a slice only relative imports. The one exception is FSD's cross-import between entities: an entity takes a sibling only through the sibling's `@x/<consumer>.ts` (`entities/message/@x/chat.ts` for `entities/chat`). This is enforced with `no-restricted-imports` per layer, as in carrier-crm's `eslint.config.js`. Segments: `api/` (transport + TanStack Query `queryOptions`, owns `baseKey`), `model/` (types, hooks, state), `ui/`, `lib/`, `config/`. Server state lives in TanStack Query, and API/WS types come from `packages/shared`.

- Requests go through `shared/api` (`http.get/post/…`): same origin, session cookies, an API error becomes `ApiError` with the server's `{ error }` text as `message` (shown to the user as is, like the old client). Response types are `z.infer<typeof …>` of the `@shalter/shared` schemas.
- WebSocket is `shared/api/ws.ts` (the `ws` singleton: ping every 20 s, backoff reconnect, `ws:reconnected` on every open, close 4001 → reason from `GET /api/sessions` as `ws:revoked`). Event types are `WsEvents` built from the `@shalter/shared` WS schemas; components subscribe with `useWsEvent`, connection status is `useWsStatus`. `app/model/use-realtime.ts` starts it while someone is signed in; sign-out stops it before the request.
- Routing is in `app/router.tsx` (`createBrowserRouter`); `app/ui/session-gate.tsx` sends a visitor without a session to `/login`, loads `/api/bootstrap` into the chat and folder query caches and starts the socket. The shell (`widgets/app-shell`, composed with the routes in `app/ui/app-routes.tsx`) stays mounted across navigation, with the chat list (`widgets/chat-list`) as its sidebar and the bottom navigation bar; on a desktop the side sections (contacts, calls, archive, settings) open over the list while the open chat stays on the right, on a phone the screen shows either the list or one screen. The list lives on WS events: the message goes into the preview at once (`entities/chat` `chatCache`), and one refetch per burst (1.2 s after message events) reconciles the counters; polling is only a fallback (30 s with the socket open, 15 s without, never in a hidden tab). Long lists are virtualized with TanStack Virtual.
- Styles are CSS modules next to the component (`*.module.css`) on the tokens in `shared/ui/tokens.css` (the same colors as `public/styles/base.css`). User-facing text is Russian. Markup keeps the roles and names the Playwright scenarios look for (buttons, not menuitems/tabs, unless a scenario expects them).
- Tests are `*.test.tsx` next to the source (Testing Library; `shared/lib/test` fakes `fetch` and `WebSocket`). jsdom has no layout: a test rendering a virtualized list stubs `HTMLElement.prototype.offsetHeight`/`offsetWidth`. Query updates reach components a tick later, so wait (`waitFor`, or advance fake timers) after a WS event.

## Rules that hold across the migration

- **Feature freeze until the core (auth, chats, messages, uploads, WS, calls) is migrated** (decided 2026-10-21): no new features in either backend, only bug fixes.
- **New backend code is TypeScript in `apps/api`.** Don't add new modules to `server/`. Fix bugs where the code currently lives.
- **Never mount the legacy app as an Express sub-app inside Nest.** Express 5 (Nest) would swap its req/res prototypes. Keep the wrappers in `src/legacy/`.
- **Behaviour doesn't change during a move.** A migrated module is done when its contract tests are green on `TARGET=nest` without edits to the tests. Any intentional behaviour change in either backend must keep `npm run test:contract` green on both targets.
- **Contract tests are black-box** (HTTP/WS only, never import `server/` or `apps/`). Write tests for a module before migrating it if it has none.
- **Data:** SQLite at `data/app.db` (`better-sqlite3`, schema in `server/db.js`), accessed only through the `server/data/*.js` modules or, in `apps/api`, through repositories built on Drizzle (`apps/api/src/modules/db`: `DbModule` wraps the very connection `server/db.js` opens, and queries stay synchronous). `server/db.js` owns the schema: `apps/api/src/modules/db/schema.ts` only describes it (columns and primary keys), `schema.spec.ts` (`npm run test:api`) fails on drift, and drizzle-kit `generate`/`migrate`/`push` are not used until `server/` is gone. A schema change goes into `server/db.js` first, then re-run `npx drizzle-kit pull` in `apps/api` (or edit `schema.ts` by hand). Never query the connection from a route handler, controller or service. Relational data (chat membership, call participants) lives in join tables. Nested, never cross-queried fields stay as JSON TEXT columns on the parent row. Encrypted data (messages, files, key rotation) must stay byte-compatible: `packages/contract-tests/compat` is the fixture that proves it.
- **One API process per `data/` directory.** Typing presence and WS connections are in-memory. The background worker (`apps/api/dist/worker.js`; `server/worker.js` when `server/index.js` runs) is forked by the runtime itself for timer sweeps and the `background_jobs` queue, and reaches clients only by relaying WS events (`server/lib/workerBridge.js`; in Nest `RealtimeService` relays by itself in the worker, `RealtimeRelayModule`). Never start it separately. Sweeps don't run on a timer in test mode; a contract test runs one pass with `POST /api/test/sweeps/:name` (test mode only, `now` in the body moves the sweep's clock), and the pass runs in the worker.
- Call signaling is WebSocket-first (`server/ws.js`, in Nest `modules/realtime/ws.gateway.ts`, which hands `call:signal:send` to `CallSignalsService` in `modules/calls`). HTTP polling is only a reconnect fallback, and both paths store the signal the same way. The client side is `apps/web` (`features/call`, socket `shared/api/ws.ts`).
- **WS events in Nest go through `RealtimeService`** (injected, `RealtimeModule` is global), never through `server/ws.js`. The WS protocol (`{ type, … }` both ways, cookie auth on upgrade, close code 4001) is why the gateway is a plain provider on Nest's HTTP server and not a `@nestjs/websockets` gateway.
- Deploys are done by someone else: any server-side step goes into DEPLOY.md as runnable commands.
